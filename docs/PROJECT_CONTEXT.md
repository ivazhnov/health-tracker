## Зачем нужен проект

Мы создаём приватное русскоязычное веб-приложение для семейного хранения лабораторных анализов. Пользователь выбирает человека, загружает PDF или изображения, проверяет распознанные данные и после подтверждения получает историю показателей с графиками и ссылками на исходники.

## Согласованный план

Полная спецификация находится в `docs/PROJECT_PLAN.md`. Текущий статус разработки ведётся отдельно в корневом `PROGRESS.md`.

- В MVP два профиля: муж и жена.
- Один общий пароль, все данные видны обоим.
- Сначала пользователь выбирает профиль, затем загружает несколько документов.
- На каждый файл создаётся отдельная постоянная ImportSession.
- Каждый документ нужно проверить и подтвердить целиком.
- Оригиналы не удаляются при дедупликации.
- Совпадающие медицинские результаты объединяются, конфликтующие значения требуют подтверждения.
- Основная дата анализа — дата забора материала.
- Интерфейс русский; документы могут быть на русском, английском, французском, немецком и итальянском.
- В MVP разбираются только лабораторные анализы.
- УЗИ, заключения, AI-отчёты, тематические страницы и MCP отложены.
- На странице человека отображаются избранные показатели, последнее значение, динамика и референсы.
- Рост и вес хранятся как датированные измерения.
- Лабораторные значения, включая eGFR, в MVP не пересчитываются приложением.
- Интеграции с Gmail и Ornament не нужны: файлы загружаются вручную.
- Плановые резервные копии, экспорт и восстановление пароля не входят в MVP.

## Техническое направление

- TypeScript, Next.js и React.
- Один OCI/Docker image для локального и production-запуска.
- Docker Compose локально.
- SQLite в WAL-режиме и оригиналы документов внутри смонтированного `/data`.
- OCR и структурное извлечение подключены через небольшие интерфейсы.
- В текущем MVP Poppler извлекает текст PDF, Tesseract выполняет OCR, а детерминированный локальный парсер формирует черновик.
- Распознавание запускается синхронно после загрузки; для семейного объёма отдельная очередь и worker пока не нужны.
- Облачный или AI-провайдер можно позднее подключить за существующими интерфейсами без миграции подтверждённых данных.
- Production: GKE StatefulSet, одна реплика и ReadWriteOnce PersistentVolumeClaim.
- Специфичные для облака Kubernetes-настройки отделены от приложения.
- Общий пароль не хранится в image; контейнер получает его хеш через secret.
- Production-доступ должен использовать HTTPS ingress или приватный VPN, но конкретный вариант пока не выбран.

## Стиль разработки и тесты

- Главный принцип — KISS: код прямой, простой и понятный с первого чтения.
- Не создаём универсальные механизмы, слои и настройки без задачи, которая нужна в текущем MVP.
- Качество оцениваем по корректности, ясности и предсказуемому поведению, а не по числу паттернов или проценту покрытия.
- Полный TDD во время сборки MVP не требуется.
- Сборка, проверка типов и ручной сквозной сценарий обязательны на каждом этапе.
- Сразу тестируются только правила с высоким риском тихого повреждения данных: миграции, дедупликация, преобразование единиц и идемпотентное подтверждение импорта.
- Основной компактный набор regression-тестов добавляется после стабилизации MVP на основе поведения, которое пользователь проверил вручную.
- Не пишем snapshot-тесты, тесты тривиального кода и тесты, которые проверяют устройство реализации вместо результата.

## Правила обновления

- Данные никогда не включаются в image.
- Локальное обновление использует прежний Docker volume.
- Команда `docker compose down -v` уничтожает локальные данные и не должна использоваться для обычного обновления.
- GKE-релиз меняет image StatefulSet, но сохраняет PersistentVolumeClaim.
- Версия схемы хранится в `schema_migrations`.
- Миграции аддитивные, транзакционные и безопасные при повторном запуске.
- Удаление старых полей отделяется от релиза, который перестаёт ими пользоваться.
- Каждая новая версия проверяется на базе предыдущей версии.

## Команды локального запуска

```bash
docker compose up --build -d
docker compose ps
docker compose logs -f app
docker compose down
```

Команду `docker compose down -v` не использовать: она удаляет volume и все данные.

## Учёт прогресса

Все этапы и чекбоксы находятся в корневом `PROGRESS.md`. После каждого этапа нужно остановиться, обновить прогресс и передать пользователю короткий сценарий проверки. Следующий этап нельзя начинать без его команды.
