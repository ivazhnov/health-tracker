# Работа над проектом

Перед любой работой над проектом прочитай:

1. `PROGRESS.md` — выполненные этапы, текущая работа и следующая задача.
2. `docs/PROJECT_CONTEXT.md` — принятые решения и команды запуска.
3. `docs/PROJECT_PLAN.md` — полные требования и архитектурный план.

Пользовательские решения имеют приоритет. Если решение меняется, сначала обнови документацию, затем код.

## Учёт прогресса

`PROGRESS.md` — единственный источник статуса разработки.

- Перед началом работы сверяй его с кодом и Git.
- При старте разрешённого пользователем этапа ставь ему статус «В работе».
- После каждой завершённой подзадачи отмечай соответствующий чекбокс.
- Ставь этапу статус «Готово» только после всех указанных проверок.
- Если работа остановилась, записывай причину и точное действие для продолжения.
- Не начинай следующий этап без отдельной команды пользователя.
- Обновляй `PROGRESS.md` и `docs/PROJECT_CONTEXT.md` в том же коммите, что и связанный код.
- В итоговом сообщении всегда указывай текущий этап, выполненные проверки и следующий шаг.

Обязательные правила проекта:

- код должен быть максимально прямым, коротким и понятным;
- не добавляй абстракции, конфигурацию, слои или универсальность без текущей практической необходимости;
- предпочитай явный поток данных и небольшие функции; комментарии должны объяснять только неочевидное «почему»;
- отличное качество означает корректность, читаемость и предсказуемость, а не количество архитектурных паттернов;
- один переносимый Docker image;
- локальная разработка и проверка через Docker Compose;
- SQLite и документы находятся только в смонтированном `/data`;
- production — одна пишущая реплика StatefulSet с PersistentVolume;
- обновление image не должно заменять или очищать `/data`;
- изменения схемы базы выполняются аддитивными, повторяемыми миграциями;
- бизнес-логика не зависит напрямую от SQLite, файловой системы, Kubernetes или конкретного AI-провайдера;
- реальные медицинские документы, секреты и содержимое анализов нельзя добавлять в Git, тестовые фикстуры или логи.

Политика тестов:

- не требуй TDD и полного покрытия для каркаса, простых экранов и очевидного glue-кода;
- во время MVP обязательно проверяй сборку, типы и основной сценарий вручную;
- тест пиши сразу только для небольшого критичного правила, где ошибка может незаметно повредить данные: миграция, дедупликация, преобразование единиц или повторное подтверждение импорта;
- после стабилизации MVP добавь компактный regression suite по подтверждённому пользователем поведению;
- не пиши snapshot-тесты, тесты фреймворка, тривиальных getter/setter и проверки числа вызовов mock без проверки результата.
